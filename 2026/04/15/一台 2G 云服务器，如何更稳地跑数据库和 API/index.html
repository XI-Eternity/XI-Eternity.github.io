最近这段时间，我一直在折腾一个基于 ESP32-S3 的家庭 AI 设备项目。

一开始的设想其实很简单：设备端负责采集环境数据和语音数据，云端负责存储和提供接口，电脑端则用来图形化查看数据。听起来像是一个典型的“小型 IoT 系统”，功能上也不算特别复杂。

但真正做下来之后，我越来越强烈地感受到，这类项目最难的地方往往不是“功能能不能实现”，而是“整套系统能不能稳定跑起来”。

尤其当服务部署在一台只有 2G 内存的小云服务器上时，很多在本地看起来完全合理的方案，到了线上就可能变得脆弱。你会发现，真正拉开差距的，往往不是代码本身，而是架构拆分、服务边界、资源分配和部署方式这些更底层的选择。

这篇文章就想把这次实践完整整理一下：从 ESP32-S3 的硬件连接，到设备侧和云端的分层设计，再到数据库可视化查看方式，以及一次凌晨 OOM 之后我对整套架构的调整。过程不算“高大上”，但足够真实，也很适合正在做个人 IoT / 家庭 AI 项目的人参考。

项目目标：设备采集，云端存储，本地可视化

这个项目的目标可以概括成三件事：

  • ESP32-S3 负责采集环境和音频数据
  • 服务端负责接收、缓存、入库，并提供 API
  • 本地电脑负责图形化查看数据库内容

从一开始，我就希望这套方案尽量轻量，不依赖太重的云服务，也不让设备直接去连接数据库。因为嵌入式设备一旦和数据库耦合得太深，后面无论是改表结构、换缓存策略，还是做接口调整，维护成本都会迅速上升。

所以最终，我还是把设备、API、缓存、数据库这几层尽量拆开了。事实证明，这个决定是对的。

硬件连接：把输入、输出和传感器总线拆清楚

当前这套硬件主要包括：

  • INMP441 麦克风
  • MAX98357 I2S 功放
  • BME688 环境传感器
  • BH1750 光照传感器

我的接线思路比较直接：语音输入、语音输出、传感器总线分别独立，尽量避免互相干扰，也方便后续扩展。

I2S 录音：INMP441

  • GPIO15 -> BCLK
  • GPIO16 -> WS/LRCLK
  • GPIO17 -> SD/DOUT
  • L/R -> GND

这里 L/R 接地，对应代码中按左声道采样的配置。

I2S 播放：MAX98357

  • GPIO5 -> BCLK
  • GPIO6 -> LRC/WS
  • GPIO7 -> DIN

这个模块只负责播放，喇叭直接接功放输出，不会占用额外的控制逻辑。

I2C 总线：BH1750 + BME688

  • GPIO9 -> SCL
  • GPIO8 -> SDA

两个传感器共用一组 I2C 总线，这样布线更省，也方便统一采集数据。

其他状态输出

  • GPIO4 可以作为状态控制脚，接一个 LED 用于指示联网、唤醒或对话状态

整套引脚规划的核心优点就是清晰：麦克风走一套 I2S，功放走另一套 I2S，传感器统一走 I2C。后面如果要继续扩展状态提示、联网反馈或者更多外设，这种拆分方式会轻松很多。

云端结构：为什么我选了 TimescaleDB + Redis + Flask API

服务端这一层，我最后用的是一个很典型、也很适合 IoT 场景的组合：

  • TimescaleDB：负责历史时序数据
  • Redis：负责最新值和在线状态
  • Flask API：负责给设备提供统一读写入口

这个组合的价值不在于“新”，而在于它和设备数据的天然结构非常匹配。

TimescaleDB 适合存历史数据

凡是带有明确时间属性、需要做时间范围查询的数据，都适合放到 TimescaleDB 里。比如：

  • 某个设备最近 24 小时的温度变化
  • 一段时间内的湿度、压力、气体浓度趋势
  • 按分钟、小时、天做聚合统计

对于环境传感器这类数据来说，时序数据库的优势非常直接。尤其当你后面开始做图表、趋势分析，或者想增加异常检测逻辑时，普通关系表会越来越别扭，而时序库会顺手很多。

Redis 适合存实时状态

Redis 在这个项目里只承担两类任务：

  • 存每个设备的最新一条数据
  • 存设备在线状态的 TTL

例如设备每隔 30 秒发一次心跳，那么就可以把在线状态 TTL 设成 90 秒。这样 API 判断设备是否在线时，不需要每次都查数据库，只需要看对应的 Redis key 是否还存在。

这种模式很轻，响应也快，非常适合“状态型”数据。

Flask API 负责统一对外

设备端不直接接触数据库，而是统一访问 Flask 提供的 API。API 再去读 Redis、查 PostgreSQL，并负责鉴权、错误处理和数据组织。

这么做的原因其实很现实：

  • 嵌入式设备不适合直连 PostgreSQL
  • 数据库不应该直接暴露到公网
  • 有了 API 这一层，后续数据库结构、缓存策略、返回格式即使变化，设备端也不需要大改

从长期维护角度看，这种分层要健康得多。

一个很容易踩的坑：本机服务不要绕公网 IP

这个问题是我中途踩过的一个典型坑，而且一开始还不太容易意识到。

最开始，我的 Flask API 部署在服务器本机，但配置里的数据库地址和 Redis 地址，写的却是服务器自己的公网 IP。也就是说，API 自己访问自己这台机器上的数据库，居然绕了一圈公网。

表面看起来似乎没问题，反正目标机器还是同一台。但实际运行后，请求开始出现很奇怪的表现：有时候变慢，有时候像卡住一样不返回。

后来排查才意识到，这种写法的问题在于：一旦访问的是本机公网 IP，请求路径就不再是纯本地回环，而可能受到这些因素影响：

  • 安全组规则
  • 防火墙
  • NAT 回流
  • Docker 端口映射策略

正确的写法其实很简单，如果 API 和数据库都在同一台机器上，就应该直接写：

也就是只走本地回环，不绕公网路径。

这个问题改完之后，接口延迟和稳定性都明显好了很多。很多看起来像“网络问题”的现象，本质上其实只是路径设计不合理。

那台 2G 云服务器，是怎么在凌晨把自己搞炸的

真正让我开始重新审视部署方案的，是一次凌晨的 OOM 事故。

当时，我在一台只有 2G 内存的小云服务器上，同时跑着这些服务：

  • TimescaleDB
  • Redis
  • pgAdmin
  • RedisInsight

按直觉看，这几个服务似乎都不算特别重。Redis 本来就很轻，TimescaleDB 当时的数据量也不大，所以一开始我并没有太担心。

直到某天凌晨，服务器突然出现了明显异常：

  • 内存打满
  • 系统触发 OOM
  • 某些服务被直接杀掉
  • 云助手也开始异常

最开始我怀疑是数据库占用过高，但看了 docker stats 之后，真实情况并不是这样。

实际资源占用并不在数据库本身

当时的情况大致是：

  • TimescaleDB 内存占用并不高
  • Redis 基本可以忽略
  • pgAdmin 占用比较明显，而且 CPU 偏高
  • RedisInsight 也在持续吃内存

更关键的是，我当时把 pgAdmin 和 RedisInsight 的端口直接映射到了公网。结果它们很快就开始被各种自动化扫描器探测。

我翻 pgAdmin 日志时，里面全是这类请求：

  • GET /.well-known/security.txt
  • GET /metrics
  • GET /api/version
  • GET /v1/models
  • GET /geoserver/web/
  • 各种异常 CONNECT 请求

只要你把 Web 管理面板直接暴露到公网，被扫描几乎是必然事件，不是概率问题，只是时间问题。

最终确认的问题本质

继续查系统日志后，我确认当时发生了两件事：

  • 同一时间出现了大量公网探测请求
  • 同一时间系统触发了 OOM killer

更进一步看，最后被内核杀掉的甚至不是 pgAdmin，而是机器上另一个常驻服务的 Erlang 虚拟机进程。

这说明一个很重要的事实：pgAdmin 和 RedisInsight 未必是唯一元凶，但它们把服务器的内存余量压得太低，导致整台小机器失去了缓冲空间。一旦叠加扫描流量和其他后台服务压力，系统就更容易触发 OOM，最后谁先被杀，更多只是运气问题。

这次事故给我的教训很明确：

在 2G 这种级别的小机器上，管理面板不应该当成常驻服务长期运行。

后来的调整：把图形化工具搬回本地电脑

事故之后，我把部署方式重新整理了一遍。

服务器上只保留最核心的常驻服务：

  • TimescaleDB
  • Redis
  • API 服务

而这些图形化工具，不再作为线上长期运行的组件：

  • pgAdmin
  • RedisInsight

再往后，我干脆连“按需启动”都不太用了。因为我发现，数据库图形化查看这件事，对个人项目来说最舒服、最省资源、也最安全的方式，其实是把工具装在自己的电脑上，通过 SSH 隧道去访问服务器。

现在我是怎么图形化看数据库的

现在我的方案很简单：本地装客户端，通过 SSH 隧道连接远程服务。

查看 PostgreSQL / TimescaleDB

我本地用的是 DBeaver。

连接参数填写如下：

  • Port: 5432

  • User: 你的数据库用户

这样就可以直接查看表结构、查询结果和数据内容，不需要在线上再跑一个 pgAdmin。

为什么 ESP32 只应该访问 API

做完这一轮之后，我对这个原则基本已经非常确定了：

ESP32 不应该直连数据库，而应该只访问 API。

例如，设备只需要请求这样的接口：

  • /api/latest/<device_id>
  • /api/history/<device_id>
  • /api/status/<device_id>

设备端负责的事情应该尽量简单：

  • 发请求
  • 带上 API Key
  • 获取 JSON
  • 解析结果

至于这些问题，应该交给 API 去处理：

  • 先查 Redis 还是先查数据库
  • 查询失败时如何降级
  • 某个设备是否在线
  • 返回数据如何组织

这样设备逻辑会干净很多，也不需要理解数据库、连接池、缓存策略这些服务端细节。对嵌入式设备来说，这种隔离非常重要。

如果现在重新总结，我最认可的架构是这样的

经过这轮实践之后，我现在最认可的整体结构大概是：

设备层

  • ESP32-S3
  • 负责采集、播放、联网和请求 API

服务层

  • Flask 或其他轻量后端
  • 负责鉴权、缓存访问、数据库读写和接口返回

数据层

  • TimescaleDB：负责历史数据
  • Redis：负责实时状态和最新值

可视化层

  • 不放在服务器上
  • 放在本地电脑上
  • 通过 SSH 隧道 + 本地图形客户端 完成访问

这套结构最大的优点，不是它有多“高级”，而是它非常适合小机器，也非常适合个人项目：足够简单，资源占用可控，后续也容易继续扩展。

这次折腾下来，我最认可的几条经验

如果把这次实践压缩成几条最有价值的经验，我觉得大概就是下面这些：

1. 设备不要直连数据库

数据库应该是服务端内部资源，设备访问 API 永远比设备访问数据库更合理。

2. 小内存服务器最怕“看起来不重”的常驻服务

很多 Web 管理面板平时存在感不强，但常驻就意味着持续的内存占用、后台进程开销和额外风险。对 2G 级别的小机器来说，这些东西叠加起来很容易出问题。

3. 公网暴露的管理面板迟早会被扫

不是“会不会”，而是“什么时候”。pgAdmin、RedisInsight 这种工具不适合直接开放到公网。

4. 本机服务就该走 127.0.0.1

这是一个很基础、但又特别容易忽略的原则。很多莫名其妙的卡顿，本质上不是代码问题，而是网络路径设计错了。

5. 本地图形化 + SSH 隧道，非常适合个人项目

更安全，更省服务器资源，使用体验也并不差，甚至往往更稳定。

结尾：功能实现只是开始，系统稳定才是真正的分水岭

做这个项目之前，我更在意的是设备能不能连上、数据能不能存进去、语音能不能跑起来。真正做完这一轮之后，我反而越来越确定：决定项目质量的，往往不是“能不能跑”，而是“能不能长期稳定地跑”。

比如：

  • 服务应不应该暴露公网
  • 设备和数据库之间要不要隔一层 API
  • 小服务器上哪些服务能常驻，哪些必须按需使用
  • 本地工具和线上服务应该怎么分工

很多项目不是死在“不会做”，而是死在“虽然能跑，但跑不稳”。

对我来说，这次从 ESP32-S3 硬件接线、AI 接入、Flask API、TimescaleDB/Redis，再到 OOM 排查和数据库可视化方式调整的整个过程，更像一次完整的系统设计训练。它把原来一些零散的想法，慢慢整理成了一套可以持续演进的结构。

如果后面继续扩展更多设备、主动告警，或者更完整的 AI 对话流程，我大概率还是会沿着这套思路继续往前做。因为至少目前看，它足够轻，也足够稳。

如果你也在做类似的个人 IoT / 家庭 AI 项目，希望这篇文章能帮你少踩几个坑。
